HTTP Header Explainer

Paste a response head and this page reads it back line by line, saying what will actually happen. HTTP headers raise no error when you get them wrong. A cookie with SameSite=None and no Secure is dropped by the browser without a word. This page names those places.

This page makes no network requests. All parsing happens in your browser; once loaded it works offline. Nothing you paste — the session id in a Set-Cookie, an Authorization header — is sent anywhere. URLs in the headers are never fetched either.

    Self-check

    What this page computes for itself
    • The parsing does not use the browser Headers object; it is written here. It follows RFC 9110 and 9112: which characters a name may contain, how whitespace around a value is dropped, how repeats of one name are joined, and folding with leading whitespace.
    • The freshness lifetime is computed with the formula in RFC 9111. It looks at s-maxage, then max-age, then Expires − Date, and if none of those are there it falls back to a guess from Last-Modified (10% of the elapsed time). Age comes from Age plus the time since Date.
    • Written by hand, it can drift. So it is checked against this browser Headers object every time the page loads, and the result is printed in the self-check panel: name normalisation, whitespace around values, how repeats join, and which characters are refused.
    • What it does not do, said plainly. Content-Security-Policy is only listed directive by directive; this page does not decide whether a given URL would pass the policy. Structured fields (RFC 8941) are read only as far as their dictionary and list shapes.
    • The header values themselves are never rewritten, not by one byte. The reading is shown in a separate column.
