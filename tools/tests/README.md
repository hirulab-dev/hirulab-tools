どれも **ページの中の計算部分をそのまま取り出して**、別の実装・別のデータと突き合わせる形です。

## test_railroad.py の考えかた

鉄道図は「正しい絵」を別の実装から借りてくることができません。**代わりに2つの性質を測ります。**

1. **受け付ける／拒む が、ブラウザの `RegExp` と一致するか。**
   自前パーサが通した式はブラウザも通し、拒んだ式はブラウザも拒む。
   ランダムな式に加えて、**わざと壊した式**(括弧を余らせる・`{3,1}`・`[z-a]` など)も当てます。
   ここでいちばん多く落ちたのは ECMAScript の後方互換(Annex B)まわりでした。
   `\x4` や `\u12` は **エラーにならず**「x のあとに 4」として読まれる、といった規則です。
   `u` フラグを付けると逆にエラーになるので、**フラグの有無どちらでも**当てています。

2. **図から作った例文字列が、元の正規表現にマッチするか。**
   解析結果(＝図)だけを見て文字列を組み立て、それを元の式に当て直します。
   図の読み方と式の意味が食い違っていたら、ここで落ちます。
   同じ例を **Python の `re`** にも当てます。参照をブラウザだけにすると、
   ブラウザと自分が同じ勘違いをしたときに気づけないためです。

⚠ 2 は「安全な形」の式だけで回します。くり返しの中がくり返しになっている式は、
こちらの生成が1つでも外れた瞬間に正規表現エンジンが指数時間に入り、ブラウザごと止まります。
パーサの検査(1)はその形も含めて全部当てますが、例文字列を当てるのは安全な形に限っています。

検査自体が空振りしていないことは、**わざと4種類のバグを仕込んで**全部検出できるかで確かめました
(量指定子 `?` を無効化 → 1が落ちる / `\d` の見本に文字を混ぜる → 2と3が落ちる /
図の幅を0にする → 4が落ちる / 同名グループの検査を外す → 1が落ちる)。

## test_regex_why.py の考えかた

この道具は2つの中身を持っています。**それぞれに別の正解を当てます。**

1. **自前のバックトラック照合器**（止まった位置を出すために要る）
   → ブラウザの `RegExp` と、**マッチするか・どこからどこまで・各グループの中身**を全部突き合わせます。
   ランダム生成した式に、後方参照・名前つきグループ・先読み・後読みを混ぜた手書きのケースを足しています。
   全角数字・ノーブレークスペース・BOM・似たハイフンも入力の文字集合に入れてあります
   (入れる前は「`\d` が全角数字にも当たる」というバグを仕込んでも捕まえられませんでした)。

2. **「止まった位置」の主張が本当か**
   道具は「N文字目で止まった。ここで待っていたのは X だ」と言います。
   その X を**ブラウザの `RegExp` に作り直して N文字目の文字に当て直します**。
   当たってしまったら、待っていたという主張が嘘です。
   自前の照合器を使わずに検算するので、1 とは独立した検査になります。

3. **「こうすればマッチします」が当たるか**
   マッチする組を用意して、**正解の分かっている壊し方**を1つだけ適用します
   (末尾に空白／全角化／BOM／CRLF／ノーブレークスペース／似たダッシュ／大文字化／ゼロ幅文字／異体字セレクタ)。
   壊れてマッチしなくなったら、道具が**その壊し方に対応する直し方**を挙げられるかを見ます。
   正解は生成側が握っているので、道具の自己申告になりません。

4. **解析器が鉄道図ツールと1バイトも違わないか**
   この道具は 17本目（鉄道図）の解析器をそのまま使っています。
   「同じものを使っている」と画面に書いてある以上、機械で確かめます。

検査が空振りしていないことは、`--sabotage` で **わざと4種類のバグを仕込んで**確かめました
(`\d` を全角数字にも当てる → 1が落ちる / 貪欲と最小一致を入れ替える → 1が落ちる /
全角を直す手当てを消す → 3が落ちる / 文字クラスの照合を常に外す → 1と2が落ちる)。

★ この突き合わせで**自分のバグを1件見つけました**。後読み `(?<=…)` を
「その位置で終わる開始点を左から探す」形で近似していたところ、7,697 件のうち **3 件**で
グループの中身がずれました。仕様どおり**右から左へ照合する**形に書き直して 0 件になっています。

## 対象外にした件数を毎回出す

検証は「見なくていい」と決めた件（読めない式、打ち切りに掛かった件、など）を必ず持ちます。

## test_password.py の考えかた

この道具の主張は「拒否サンプリングは偏らない・素朴な剰余法（`v % n`）は偏る」ことです。
偏りは**確率的な性質**なので、参照実装に当てて一致・不一致を数える他のスクリプトとは
測り方が違います。

1. **実際にブラウザで `crypto.getRandomValues` を使って何万回も引かせる。**
   理屈だけでなく、ページの `rejectionIndices` / `naiveModIndices` をそのまま呼びます。
2. **χ²統計量を計算し、SciPyの非心χ²分布(`scipy.stats.ncx2`)で「理論上どれくらいの
   確率で偏りを検出できるはずか」を計算する。**
   256 が n を割り切らないとき、剰余法は先頭 `256 % n` 文字を `floor(256/n)+1 / 256`、
   残りを `floor(256/n) / 256` の確率で選びます。この理論分布から非心度 λ を計算し、
   固定回数の実験でどれだけの確率で有意な偏りが検出できるはずかを予測します。
3. **実測の検出回数が、その理論上の確率と二項分布として矛盾しないかを見る。**
   ★ 最初は「9割の試行で偏りが検出されるはず」という決め打ちのしきい値を使っていましたが、
   **n=3 や n=10 のような小さい n では、理論上の偏りそのものが小さく検出されにくい**
   ことが分かりました（n=62 では非心度 λ≈260 だが n=3 では λ≈1 程度）。
   固定しきい値は統計的に不適切だったので、理論値との整合性で判定する形に書き直しました。
4. **拒否サンプリングは、どのnでも「有意水準アルファそのもの」の頻度でしか
   検出されないはず**（＝理論上まったく偏らない）ことも同時に確認します。
5. **χ²のp値近似(Wilson–Hilferty)自体をSciPyの正確な値と突き合わせる**（144件）。
   近似の精度を主張するなら、近似の精度そのものを検証しないと意味がありません。
6. **正解の分かっている落とし穴の名指し**（13件）と、**開発中に実際に踏んだ回帰バグの検査**
   （「各文字種を必ず1つ以上含める」機能が、別の文字種の唯一の出現を上書きして
   新たに欠落させていたバグ。数千回に数回の頻度で発生していました）。

`--sabotage` で**5種類のバグを仕込んで、5種類とも狙った検査が落ちること**を確認しています
（そのうち1つは、上に書いた実際に踏んだ回帰バグそのものです）。
