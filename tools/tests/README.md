どれも **ページの中の計算部分をそのまま取り出して**、別の実装・別のデータと突き合わせる形です。

## 出力の読み方

**不一致** と **既知のデータ版差** を分けて数えます。後者は「ブラウザに入っている
タイムゾーンデータが Python 側より古い」ことによる差で、ツールの誤りではありません。
2026-08-22 時点では `America/Vancouver` と `Africa/Casablanca` の2件が該当します
(どちらも2026年秋以降の規則変更にブラウザのICUが追いついていない)。
ブラウザが追いつけば、この2件は自然に消えます。

スクリプト先頭の `KNOWN` に、その差をいつから既知とみなすかを日付つきで書いてあります。
**その日付より前で割れたら本物の不一致**として落ちます。

## test_csv.py の考えかた

セルの正解は、**書き出す前に持っていた元の行そのもの**です。
ブラウザと同じ手順を Python で書き直しても、同じ勘違いをすれば同じ答えになって
気づけないので、参照側は「書き出す前の値」という別の出どころにしています
(`csv.writer` → `csv.reader` で往復できることは、そのつど別に確かめています)。

文字コードは UTF-8 / UTF-8 BOM / CP932 / EUC-JP / UTF-16 の5通りで書き出し、
判定器が当てられるかを数えます。**ASCIIだけになった回は「判定不要」として別に数えます**
(どの文字コードで読んでも同じ結果になるので、当たっても実力ではない)。
区切り文字も同様に、**どちらでも列数がそろってしまう形の回は除外**して数えます。

## test_railroad.py の考えかた

鉄道図は「正しい絵」を別の実装から借りてくることができません。**代わりに2つの性質を測ります。**

1. **受け付ける／拒む が、ブラウザの `RegExp` と一致するか。**
   自前パーサが通した式はブラウザも通し、拒んだ式はブラウザも拒む。
   ランダムな式に加えて、**わざと壊した式**(括弧を余らせる・`{3,1}`・`[z-a]` など)も当てます。
   ここでいちばん多く落ちたのは ECMAScript の後方互換(Annex B)まわりでした。
   `\x4` や `\u12` は **エラーにならず**「x のあとに 4」として読まれる、といった規則です。
   `u` フラグを付けると逆にエラーになるので、**フラグの有無どちらでも**当てています。

2. **図から作った例文字列が、元の正規表現にマッチするか。**
   解析結果(＝図)だけを見て文字列を組み立て、それを元の式に当て直します。
   図の読み方と式の意味が食い違っていたら、ここで落ちます。
   同じ例を **Python の `re`** にも当てます。参照をブラウザだけにすると、
   ブラウザと自分が同じ勘違いをしたときに気づけないためです。

⚠ 2 は「安全な形」の式だけで回します。くり返しの中がくり返しになっている式は、
こちらの生成が1つでも外れた瞬間に正規表現エンジンが指数時間に入り、ブラウザごと止まります。
パーサの検査(1)はその形も含めて全部当てますが、例文字列を当てるのは安全な形に限っています。

検査自体が空振りしていないことは、**わざと4種類のバグを仕込んで**全部検出できるかで確かめました
(量指定子 `?` を無効化 → 1が落ちる / `\d` の見本に文字を混ぜる → 2と3が落ちる /
図の幅を0にする → 4が落ちる / 同名グループの検査を外す → 1が落ちる)。

## test_regex_why.py の考えかた

この道具は2つの中身を持っています。**それぞれに別の正解を当てます。**

1. **自前のバックトラック照合器**（止まった位置を出すために要る）
   → ブラウザの `RegExp` と、**マッチするか・どこからどこまで・各グループの中身**を全部突き合わせます。
   ランダム生成した式に、後方参照・名前つきグループ・先読み・後読みを混ぜた手書きのケースを足しています。
   全角数字・ノーブレークスペース・BOM・似たハイフンも入力の文字集合に入れてあります
   (入れる前は「`\d` が全角数字にも当たる」というバグを仕込んでも捕まえられませんでした)。

2. **「止まった位置」の主張が本当か**
   道具は「N文字目で止まった。ここで待っていたのは X だ」と言います。
   その X を**ブラウザの `RegExp` に作り直して N文字目の文字に当て直します**。
   当たってしまったら、待っていたという主張が嘘です。
   自前の照合器を使わずに検算するので、1 とは独立した検査になります。

3. **「こうすればマッチします」が当たるか**
   マッチする組を用意して、**正解の分かっている壊し方**を1つだけ適用します
   (末尾に空白／全角化／BOM／CRLF／ノーブレークスペース／似たダッシュ／大文字化／ゼロ幅文字／異体字セレクタ)。
   壊れてマッチしなくなったら、道具が**その壊し方に対応する直し方**を挙げられるかを見ます。
   正解は生成側が握っているので、道具の自己申告になりません。

4. **解析器が鉄道図ツールと1バイトも違わないか**
   この道具は 17本目（鉄道図）の解析器をそのまま使っています。
   「同じものを使っている」と画面に書いてある以上、機械で確かめます。

検査が空振りしていないことは、`--sabotage` で **わざと4種類のバグを仕込んで**確かめました
(`\d` を全角数字にも当てる → 1が落ちる / 貪欲と最小一致を入れ替える → 1が落ちる /
全角を直す手当てを消す → 3が落ちる / 文字クラスの照合を常に外す → 1と2が落ちる)。

★ この突き合わせで**自分のバグを1件見つけました**。後読み `(?<=…)` を
「その位置で終わる開始点を左から探す」形で近似していたところ、7,697 件のうち **3 件**で
グループの中身がずれました。仕様どおり**右から左へ照合する**形に書き直して 0 件になっています。

## 対象外にした件数を毎回出す

検証は「見なくていい」と決めた件（読めない式、打ち切りに掛かった件、など）を必ず持ちます。
**除外の理由がバグと相関していると、壊した分だけ検査の外に出てしまい、検査が空振りします。**
実際に一度そうなった（`test_replace.py` の `--sabotage` で仕込んだ欠陥が捕まらなかった）ので、
`skipwatch.py` を通して**対象外の件数を毎回表に出し、前回の割合と比べる**ようにしました。
増えていれば ★ が付きます。

## `test_headers.py` — HTTPヘッダの読み下し

対象: https://hirulab-dev.github.io/hirulab-tools/headers/

道具が主張していることを分け、**それぞれ別の出どころの正解**を当てています。
参照が1つだと、こちらと参照が同じ勘違いをしたときに気づけないからです。

1. **分解した結果 vs ブラウザの `Headers`**（400件）
   名前の正規化・値の前後の空白の落とし方・同じ名前が複数来たときの結合。
   ★ `Set-Cookie` だけは**わざと違います**。fetch の `Headers` は `get()` でカンマ結合しますが、
   HTTP では Set-Cookie を結合してはいけません（`Expires` の値自体にカンマが入るため）。
   その差が出ること自体を1件確かめています。
2. **受け付ける／拒む** — ここは「この道具 vs ブラウザ」では測れません。**規格と fetch が本当に違う**からです。
   RFC 9110 の field-value に制御文字は置けませんが、fetch が拒むのは `0x00` `0x0A` `0x0D` だけ。
   さらに fetch は前後の「HTTPの空白」を落としますが、**そこに CR と LF が入っています**
   （規格の OWS は SP と HTAB だけ）。なので2つのモデルを別々に書き、
   **この道具は RFC 側と、ブラウザは fetch 側と一致するか**をそれぞれ見ています。
3. **HTTP日付 vs Python `email.utils`**（272件）— IMF-fixdate / RFC 850 / asctime。
   ★ **2桁の年の読み方は規格と Python で本当に違います**（RFC 9110 は「50年以上先に見えるなら前世紀」、
   Python は「70未満なら2000年代」）。この道具は RFC 側なので、
   食い違う帯は**差が出ることを確かめる**形で検査しています。
4. **Set-Cookie の属性 vs Python `http.cookies`**（400件）
5. **Content-Type vs Python `email.message`**（400件）
6. **キャッシュの寿命 vs RFC 9111 の式**（400件）
   ⚠ これだけは第三者の実装ではなく、規格の式を Python で別に書いたものです。
   同じ人が両方を書いている以上、1〜5 ほどの強さはありません。そう分かった上で使うものです。
7. **正解を握った落とし穴の名指し**（48件）— `data-code` で照合するので英語版にもそのまま当たります。

★ この突き合わせで**自分のバグを1件見つけました**。`Mon, 32 Aug 2026 …` のような
**存在しない日付を通していました**（`Date.UTC` が黙って9月1日に繰り上げるため）。
組み立て直して同じ年月日に戻るかを見る形にして直しています。

`--sabotage` で**7種類のバグを仕込んで、7種類とも狙った検査が落ちること**を確認しています。

## `test_jwt.py` — JWTの読み下し

対象: https://hirulab-dev.github.io/hirulab-tools/jwt/

ここも参照を1つに寄せず、**別の出どころに散らして**います。

1. **分解した結果 vs Python の `base64` / UTF-8 / `json`**（400件）
   この道具は `atob` も `TextDecoder` も `JSON.parse` も使わず自前で書いてあるので、
   **3つとも別の標準ライブラリ**に当てる意味があります。
2. **壊れた符号化の扱い vs Python**（37件）
   長さが4で割って1余る / 字表にない文字 / overlong な UTF-8 / サロゲート / U+10FFFF 超え。
   ★ 既定の `urlsafe_b64decode` は**字表にない文字を黙って捨てる**ので参照になりません。
   `validate=True` を明示して初めて拒みます。
   「余ったビットが0でない」は Python が拒まないので、**書き戻すと別の文字列になるか**で定義しています。
3. **クレームの判定 vs PyJWT**（400件）— ここがいちばん強い参照です。
   PyJWT は別の言語の第三者実装で、`exp` が切れているか・`nbf` がまだかを自分で判断します。
   この道具の指摘（`exp-past` / `nbf-future`）と、PyJWT が投げる例外が一致するかを見ます。
4. **署名の検証 vs Python**（23件）
   ブラウザの `crypto.subtle` と Python の `hmac` / `cryptography` という**まったく別の実装どうし**。
   HS256/384/512・RS256/384/512・PS256/384・ES256/384 を、正しい鍵・違う鍵・
   中身を書き換えたもの・**DER 形式のまま入れた署名**で当てています。
5. **★「規格が拒む形」と「実装が拒む形」は違う**
   RFC 7515 は base64url の詰め（`=`）を書いてはいけないと決め、`+` `/` も認めません。
   ところが **PyJWT はどちらも受け取り、署名の検証まで通します**（この検査で 73 / 73 件）。
   この道具は**拒みません**（貼られたものを読んで説明するのが仕事なので）。
   代わりに `b64-padding` / `b64-standard` / `b64-slack` で名指しします。
   つまりここは「拒むか」ではなく「名指しできるか」で測るのが正しい、という切り分けです。
   ★ 参照が何も拒まないだけだと検査が空振りするので、
   **明らかに壊れたトークンを PyJWT が本当に拒むこと**を先に確かめています。
6. **正解を握った落とし穴の名指し**（57件）— `data-code` で照合するので英語版にもそのまま当たります。
7. **ページ内の自己検査**（6件）— 道具自身がその場で `atob` / `TextDecoder` / `JSON.parse` と
   突き合わせている欄が、全部 ✓ になっているか。

`--sabotage` で**8種類のバグを仕込んで、8種類とも狙った検査が落ちること**を確認しています。
★ 最初の版では**3種類が空振りしました**（余りビットの片方の枝 / 長さが4で割って1余る形 /
overlong な UTF-8）。どれも**検査データにその形が1件も無かった**のが原因です。
2 の検査はそのために足しました。

## test_password.py の考えかた

この道具の主張は「拒否サンプリングは偏らない・素朴な剰余法（`v % n`）は偏る」ことです。
偏りは**確率的な性質**なので、参照実装に当てて一致・不一致を数える他のスクリプトとは
測り方が違います。

1. **実際にブラウザで `crypto.getRandomValues` を使って何万回も引かせる。**
   理屈だけでなく、ページの `rejectionIndices` / `naiveModIndices` をそのまま呼びます。
2. **χ²統計量を計算し、SciPyの非心χ²分布(`scipy.stats.ncx2`)で「理論上どれくらいの
   確率で偏りを検出できるはずか」を計算する。**
   256 が n を割り切らないとき、剰余法は先頭 `256 % n` 文字を `floor(256/n)+1 / 256`、
   残りを `floor(256/n) / 256` の確率で選びます。この理論分布から非心度 λ を計算し、
   固定回数の実験でどれだけの確率で有意な偏りが検出できるはずかを予測します。
3. **実測の検出回数が、その理論上の確率と二項分布として矛盾しないかを見る。**
   ★ 最初は「9割の試行で偏りが検出されるはず」という決め打ちのしきい値を使っていましたが、
   **n=3 や n=10 のような小さい n では、理論上の偏りそのものが小さく検出されにくい**
   ことが分かりました（n=62 では非心度 λ≈260 だが n=3 では λ≈1 程度）。
   固定しきい値は統計的に不適切だったので、理論値との整合性で判定する形に書き直しました。
4. **拒否サンプリングは、どのnでも「有意水準アルファそのもの」の頻度でしか
   検出されないはず**（＝理論上まったく偏らない）ことも同時に確認します。
5. **χ²のp値近似(Wilson–Hilferty)自体をSciPyの正確な値と突き合わせる**（144件）。
   近似の精度を主張するなら、近似の精度そのものを検証しないと意味がありません。
6. **正解の分かっている落とし穴の名指し**（13件）と、**開発中に実際に踏んだ回帰バグの検査**
   （「各文字種を必ず1つ以上含める」機能が、別の文字種の唯一の出現を上書きして
   新たに欠落させていたバグ。数千回に数回の頻度で発生していました）。

`--sabotage` で**5種類のバグを仕込んで、5種類とも狙った検査が落ちること**を確認しています
（そのうち1つは、上に書いた実際に踏んだ回帰バグそのものです）。
